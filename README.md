# Tech News Publisher（科技情报简讯发布器）

一个面向 AI 编程/写作代理的自定义 Skill：把一个新闻标题或话题，研究、撰写、归档成一篇可发布的 Hexo 草稿。正文面向广大用户，只写已确认内容，用白话解释必要术语，不把新闻来源、查证过程或信息空缺写进文章。

最终产物落在 `source/_drafts/` 下，**不会自动发布**——由作者审核后手动 `hexo publish`。

## 它解决了什么问题

很多 AI 工具能写文章，但写出来的几乎都是 AI 味浓重的「正确的废话」：堆形容词、爱总结升华、喜欢三段排比、动不动「炸裂」「重塑行业」。对于科技博客来说，这种内容毫无信噪比可言。

这个 Skill 的目标是把 AI 代理拉到一个具体的写作角色里——**科技情报分析师**——并通过明确的规则约束，让产出接近一个有判断力的人类编辑：

- 多源交叉验证（代码层 / 理论层 / 舆论层 / 报道层 / 官方层），三角验证核心数据
- 识别 PR 通稿场景，只保留可由权威文档、代码仓库或可复现结果确认的内容
- 未确认的信息直接剔除，不用“尚不明确”“没有官方口径”“仍待实测”等句子占位
- 面向普通用户解释“这是什么、谁能用、怎么用、要多少钱、有什么变化”
- 反对偶、反三段式、反价值升华结尾
- 默认删除空洞副词与转述层，能用数字就不用「显著提升」

## 工作流程

```
研究 → 撰写 → 创建草稿 → SEO 优化 → 交付
```

| 阶段 | 做什么 |
|------|--------|
| **Stage 1 研究** | 跨 5 个层次搜集信息，三角验证核心数据，每条信息归入 A/B/C 三档 |
| **Stage 2 撰写** | 正文使用 `article-writing` skill 基于已确认信息生成大众可读文章，用内置 Image 2 生成 5:2 封面；涉及已确认数据图表时优先插入清晰原图截图，不清晰再用 Image 2 重制 |
| **Stage 3 建草稿** | `hexo new draft "<title>"`，写入正文（去掉重复标题与来源段） |
| **Stage 4 SEO** | 切换 SEO 优化师角色，grep 现有 taxonomy，配置 permalink / categories / tags / description |
| **Stage 5 交付** | 草稿路径 + 信源列表交还用户，正文不展示信源，**不执行 `hexo publish`** |

## 触发条件

当用户提供一个科技新闻话题（产品发布、融资、论文、行业事件），并表达「写一篇文章」「整理成一篇博客」「研究一下并写出来」之类的意图时，Skill 自动触发。

即便用户没有明说「Hexo」或「博客」，只要当前工作目录是 Hexo 项目（存在 `_config.yml` 和 `source/_posts/`），Skill 也会接管。

## 前置条件

- 当前目录是 Hexo 项目根目录（`_config.yml` 与 `source/_posts/` 同级）
- `hexo` CLI 已安装并可在命令行调用
- 当前 AI 代理有可用的联网检索/浏览能力（Stage 1 需要查证外部信源）

## 反 AI 腔调规则一览

Skill 内置了非常具体的禁用清单，分三层：

**第一层：禁用词与禁用句式**

过渡套话：综上所述、总而言之、不难看出、显而易见
宏大叙事：在这个 X 的时代、X 已成为不可逆的趋势、未来可期、引发广泛关注
情绪形容词：震惊、炸裂、史诗级、王炸、封神、碾压、吊打、断崖式领先、颠覆性
AI 特征句尾：…这一突破、…这一里程碑、…为 XXX 打开了新的可能性

**第二层：句式反模式**

- **反对偶**：AI 喜欢工整对称的两段式。直接陈述，长短句混用。
- **反三段式排比**：有两点写两点，有四点写四点，绝不为对称凑数。
- **反铺垫**：核心结论先扔出来，背景跟在后面。
- **反"价值升华"结尾**：不以"这意味着…"收尾。让事实自己说话。
- **反"看似 X 实则 Y"**：AI 凑深度的标志。

**第三层：信息密度自检**

写完每段问：**这段话删掉哪些字含义完全不变？** 凡是可删的删掉。

**对照示例**

❌ AI 味：
> 随着大模型技术的不断发展，某公司近日推出了 Alpha 模型，这一突破性的发布在业内引发了广泛关注。

✅ 干练：
> 某公司发布 Alpha 模型，并已开放 API。输入价格保持不变，开发者可以沿用现有接口接入。Alpha 模型支持文本和图片输入，普通用户可通过网页端直接体验。

完整规则见 [SKILL.md](./SKILL.md) 和 `examples/tone-samples.md`。

## 三档信息区分

写作时每条信息必须归入下列三档之一，绝不混淆：

| 档位 | 含义 | 处理方式 |
|------|------|----------|
| **A 档：已确认事实** | 多源独立验证 / 一手权威文档 / 可复现数据 | 可以进入文章 |
| **B 档：单方宣称** | 有出处但无独立证据的性能、效果或市场判断 | 只留在内部研究笔记 |
| **C 档：传言** | 无明确出处的小道消息 | 直接剔除 |

PR 通稿特征明显时（中文媒体措辞高度相似），正文只提取已经确认的上线时间、使用入口、价格、规格和功能范围。营销判断、效果承诺、信源冲突和信息空缺都不进入文章，也不用“不明确”“未公布”“缺少评测”等表达占位。

## 配图

每篇文章在摘要 blockquote 之后必须插入一张封面图。正文定稿后，根据标题、摘要和 A 档已确认事实，使用内置 `image_gen`（Image 2）自动生成主题图。正文涉及已确认的数据图表时，还要把图表插入对应段落。**详细流程在 `examples/image-workflow.md`**，包括封面提示词、图表截图与重制、确认、上传和失败兜底。

硬性规则：
- 每篇文章自动生成一张 5:2 横版科技主题图，不等待用户另行提出生图要求；5:2 只约束封面，不约束正文数据图表
- 生成和修改提示词都必须明确指定 5:2；展示或上传前核对实际像素尺寸，比例不符时安全裁切或扩展画布，无法保留文字、Logo 和主体时重新生成，禁止拉伸变形
- 配图提示词只使用文章中的已确认内容，不把传言、产品宣称或未确认功能画进图片
- 封面默认使用内置 Image 2，不搜索、下载或复用网络图片；正文数据图表截图是唯一默认例外
- 图片默认无水印、无虚构 UI、无未经确认的产品细节
- 图片可以包含与文章主题相关的标题文字和已确认品牌 Logo；出现时必须检查文字准确性，Logo 不得失真或使用未确认的品牌标志
- “标题必须逐字准确”不代表封面只能保留定稿标题；除非用户明确要求仅标题版，不得自行禁止标题之外的可读文字。额外文字有 A 档事实支撑且不构成虚构 UI 时可以保留，未确认、错误或构成虚构 UI 时只修正对应元素，不用抽象字形或伪文字替代
- 不得默认在提示词中加入 `no text`、`no logo`、“无文字”或“无品牌标志”；通用 imagegen 示例和旧会话记录不能覆盖当前 skill 规则
- 标题文字应根据画面主色和品牌色建立层次：以深色中性色保证可读性，用 1–2 个协调强调色突出关键词或状态，不得默认整行只用纯黑色
- 标题配色避免彩虹化、霓虹色、低对比度和粗重描边；只需优化文字时，不改变其他准确视觉元素
- 遇到错误文字、失真 Logo 或与已确认事实冲突的视觉暗示时，只修正发生问题的元素，不得擅自扩大为整张图无文字、无品牌标志
- 已确认品牌的 Logo 失真时，先从品牌官网或官方品牌资源取得参考图并做定点修正；参考图修正后仍无法准确还原，才允许只移除该 Logo 或替换为无品牌图标，不得首次生成失真就直接无品牌化
- 无法确认的产品外观、界面、数字、图表或 Logo 不画进图片
- 避免昏暗模糊的素材库风格、视觉堆砌，以及与文章无关的机器人、全息投影、电路板、代码雨和科幻元素
- 生成后自动保存到用户桌面并展示；生成无需确认，上传前仍需用户确认
- **跑任何图片上传命令前必须先和用户确认**，等明确肯定回复才上传
- **`image` 命令失败不要默默跳过**，明确告知用户
- **绝对不要伪造 R2 URL**
- **摘要 blockquote 和配图之间不能有空行**，图片行必须紧跟摘要下一行
- **图片 Markdown 的 alt/name 不要都写“配图”**，根据文章内容和 SEO 写具体名称，例如 `![Kimi Work 办公智能体界面](...)`
- 正文讨论 A 档数据图表时，优先截取原始图表并插入对应段落；保留标题、坐标轴、图例、单位、数据标签和必要来源标记
- 在文章实际显示宽度下检查截图清晰度；文字、刻度或数据点看不清时，才用 Image 2 按原图和已核验数据重制
- 重制图必须逐项保持图表类型、标签、单位和全部数值准确，并标注“根据 <来源> 数据重制”；错字、错数或比例误导经定点修正后仍存在时，使用 `待补图`，不插入错误图

## ⚠️ 缓存与成本

本 skill 已针对 Anthropic API 的 prompt caching 优化。**对 SKILL.md 主体的任何修改都会让缓存失效**（贵 25%）。

**安全修改区**（不影响主缓存）：`examples/` 目录下的所有文件

**谨慎修改区**（会击穿缓存）：SKILL.md 本文件的任何字面修改

### 批量产文模式

连续产文时，**全部在同一个会话里连续触发本 skill**：
- 同一会话内，SKILL.md 的内容被缓存，从第 2 篇起这部分 token 价格降到 ~10%
- 跨会话（或间隔 > 5 分钟）缓存过期，按首次写入计价

实操建议：今天计划产文 ≥3 篇时，**不要关掉对话**，把多个选题在同一会话里逐个交给当前 AI 写作代理。

## 设计决策

**为什么停在草稿阶段？**

技术上让 AI 代理直接 `hexo publish` 完全可行。但发布是一个不可逆动作，且科技新闻的事实核查必须留一个人类闭环。Skill 在 Stage 5 明确写了：即使用户原始指令包含「发布到博客」，也理解为「产出一篇可直接发布的草稿」，而不是发布授权。

**为什么强制扫描已有 tag？**

新建 tag 会稀释聚合页权重。Stage 4 强制先 `grep` 已有 categories/tags，优先复用。这不是风格偏好，是 SEO 决策。

**为什么把规则写得这么死？**

「写得有人味」是个非常容易被 LLM 用礼貌话术绕过去的目标。把要求拆到禁用词清单、句式反模式、信息密度自检三层，每一层都有可对照的具体规则，反而比抽象目标更可执行。

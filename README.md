# Tech News Publisher（科技情报简讯发布器）

一个面向 [Claude](https://claude.ai/) 的自定义 Skill：把一个新闻标题或话题，研究、撰写、归档成一篇可发布的 Hexo 草稿，全程保持「科技情报分析师」的语气，反 AI 腔调，零幻觉容忍。

最终产物落在 `source/_drafts/` 下，**不会自动发布**——由作者审核后手动 `hexo publish`。

## 它解决了什么问题

很多 AI 工具能写文章，但写出来的几乎都是 AI 味浓重的「正确的废话」：堆形容词、爱总结升华、喜欢三段排比、动不动「炸裂」「重塑行业」。对于科技博客来说，这种内容毫无信噪比可言。

这个 Skill 的目标是把 Claude 拉到一个具体的写作角色里——**科技情报分析师**——并通过明确的规则约束，让产出接近一个有判断力的人类编辑：

- 多源交叉验证，区分客观事实 / 官方口径 / 未经证实
- 识别 PR 通稿场景，明确告诉读者「目前所有报道均转引官方口径」
- 反对偶、反三段式、反价值升华结尾
- 默认删除空洞副词与转述层，能用数字就不用「显著提升」

## 工作流程

```
研究 → 撰写 → 创建草稿 → SEO 优化 → 交付
```

| 阶段 | 做什么 |
|------|--------|
| **Stage 1 研究** | 跨 5 个层次（代码层 / 理论层 / 舆论层 / 报道层 / 官方层）搜集信息，三角验证核心数据 |
| **Stage 2 撰写** | 以「科技情报分析师」身份产出文章，遵循反 AI 腔调三层规范，并插入配图 |
| **Stage 3 建草稿** | 调用 `hexo new draft "<title>"`，写入正文（去掉重复标题与来源段） |
| **Stage 4 SEO** | 切换到 SEO 优化师角色，配置 permalink / categories / tags / description |
| **Stage 5 交付** | 把草稿路径与信源列表交还给用户，**不执行 `hexo publish`** |

## 触发条件

当用户提供一个科技新闻话题（产品发布、融资、论文、行业事件），并表达「写一篇文章」「整理成一篇博客」「研究一下并写出来」之类的意图时，Skill 自动触发。

即便用户没有明说「Hexo」或「博客」，只要当前工作目录是 Hexo 项目（存在 `_config.yml` 和 `source/_posts/`），Skill 也会接管。

## 前置条件

- 当前目录是 Hexo 项目根目录（`_config.yml` 与 `source/_posts/` 同级）
- `hexo` CLI 已安装并可在命令行调用
- Claude 处于可联网状态（Stage 1 需要 web search）

## 反 AI 腔调规则一览

Skill 内置了一份非常具体的禁用清单，节选：

**禁用过渡套话**：综上所述、总而言之、不难看出、显而易见

**禁用宏大叙事**：在这个 X 的时代、X 已成为不可逆的趋势、未来可期、引发广泛关注

**禁用情绪形容词**：震惊、炸裂、史诗级、王炸、封神、碾压、吊打、断崖式领先、颠覆性

**禁用 AI 特征句尾**：...这一突破、...这一里程碑、...为 XXX 打开了新的可能性

**对照示例**

❌ AI 味：
> 随着大模型技术的不断发展，Anthropic 公司近日推出了 Claude 4.7 模型，这一突破性的发布在业内引发了广泛关注。

✅ 干练：
> Anthropic 发布 Claude 4.7。MMLU 88.7，比 4.6 提高 1.2 分；SWE-bench Verified 62%，提高 3 个百分点。API 定价与 4.6 持平。

完整规则见 [SKILL.md](./SKILL.md)。

## 三档信息区分

写作时每条信息必须归入下列三档之一，绝不混淆：

| 档位 | 含义 | 处理方式 |
|------|------|----------|
| **A 档：客观事实** | 多源独立验证 / 一手官方文档 / 可复现数据 | 直接陈述，不加不确定性标记 |
| **B 档：官方口径** | 有出处但无第三方验证 | **必须显式归因**：「官方称…」「据 OpenAI 博客…」 |
| **C 档：传言** | 无明确出处的小道消息 | 标「待核实」或直接剔除 |

PR 通稿特征明显时（中文媒体措辞高度相似），明确告诉读者：「目前所有报道均转引官方口径，暂无第三方独立评测/复现。」——这本身就是有价值的可信度信号。

## 配图规范

每篇文章在摘要 blockquote 之后必须插入一张配图。流程如下：

| 步骤 | 做什么 |
|------|--------|
| **1. 选图** | 优先使用信源官方配图（产品截图、海报、benchmark 图表）；若无，则对官方发布页/GitHub release 页面截图。禁止使用无关的 generic stock photo |
| **2. 下载** | 把图片保存到本地（如 `/tmp/cover.png`） |
| **3. 确认** | 上传前必须向用户展示选图来源、本地路径和图片说明，等待用户明确同意 |
| **4. 上传** | 用户确认后运行 `image <本地路径>` 命令上传到 Cloudflare R2 |
| **5. 插入** | 把返回的 markdown 图片链接放在 blockquote 摘要之后、第一个 `## 技术/事件点` 之前 |
| **6. 兜底** | 上传失败时明确告知用户，绝不伪造 URL |

alt text 使用简短中文描述（如 `Claude 4.7 发布页截图`），便于 SEO 和无障碍阅读。

PR 通稿特征明显时（中文媒体措辞高度相似），明确告诉读者：「目前所有报道均转引官方口径，暂无第三方独立评测/复现。」——这本身就是有价值的可信度信号。

## 设计决策

**为什么停在草稿阶段？**

技术上让 Claude 直接 `hexo publish` 完全可行。但发布是一个不可逆动作，且科技新闻的事实核查必须留一个人类闭环。Skill 在 Stage 5 明确写了：即使用户原始指令包含「发布到博客」，也理解为「产出一篇可直接发布的草稿」，而不是发布授权。

**为什么强制扫描已有 tag？**

新建 tag 会稀释聚合页权重。Stage 4 强制先 `grep` 已有 categories/tags，优先复用。这不是风格偏好，是 SEO 决策。

**为什么把规则写得这么死？**

「写得有人味」是个非常容易被 LLM 用礼貌话术绕过去的目标。把要求拆到禁用词清单、句式反模式、信息密度自检三层，每一层都有可对照的具体规则，反而比抽象目标更可执行。
